我的第一次SRC挖洞：从B站评论区到被黑的政府网站

2026-09-13 admin SRC

从一条可疑链接到完整攻击链：一次脱敏后的SRC溯源记录

前言

这是我的第一次SRC漏洞挖掘经历。

整个过程从一个视频平台评论区的可疑链接开始，最终追出了一条完整的攻击链：某视频平台客户端漏洞 → 黑产跳板域名 → 被篡改的政府网站页面。

虽然最终平台SRC判定为“内部已知”，没有给奖励，但这次经历让我完整走通了“发现→分析→溯源→上报”的全流程，也让我真正理解了什么是“攻击链思维”。

这篇文章记录了整个过程，希望能给同样刚入门的安全研究者一些参考。本文已对真实域名、URL、路径、编号、单位、时间等信息进行脱敏处理。

一、偶然的发现

事情很偶然。那天我像往常一样刷某视频平台，在某个视频的评论区里，看到了一条奇怪的链接：

https://d.example.com/download_app.html?from_spmid=...&plat_id=...&preUrl=<十六进制编码>&schema=...&share_from=h5

域名是 d.example.com，看起来是平台官方的下载页。但后面的参数特别长，而且 preUrl 的值是一长串十六进制编码，这立刻引起了我的注意。

正常情况下，一个下载页的跳转参数不需要这么复杂。我决定把它复制下来，先在电脑浏览器里分析，而不是直接在App里点开。

二、解码与漏洞确认

把 preUrl 参数的值进行十六进制解码后，得到了类似这样的内容：

appscheme://mall/web?url=http://trusted.example@malicious.example/?demo

看到这个，我立刻意识到问题所在。

这是一个平台客户端的自定义 URL Scheme，其中 mall/web 模块用于在内置 WebView 中加载指定的 URL。而这个 URL 参数的值是：

http://trusted.example@malicious.example/

根据 URL 标准规范（RFC 1738），@ 符号之前的部分被解析为用户名和密码认证信息，实际请求的主机名是 @ 之后的部分，也就是 malicious.example。

但是，平台客户端在进行域名白名单校验时，可能只是简单地截取了 :// 到第一个 / 之间的字符串，误将 trusted.example 识别为目标主机，从而认为这是一个合法的平台域名，通过了校验。

校验层以为自己在访问平台域名，浏览器内核却在访问 malicious.example。这就是典型的“URL解析不一致”漏洞。

三、溯源：从跳板到政府网站

确认漏洞原理后，我并没有停下。我访问了 malicious.example，发现它只是一个简单的跳转页，迅速将我重定向到了一个全新的地址：

https://gov.example/path/...?...

当我看到政府网站域名时，心里咯噔一下。

这是某地政府机关的官方网站。

也就是说，攻击链是这样的：

某视频平台客户端漏洞 → 黑产跳板域名 → 被篡改的政府网站页面

攻击者利用平台客户端的漏洞作为入口，将用户流量导向黑产域名，最终落地在一个被篡改的政府网站上展示非法内容。这样做的目的是利用政府域名的公信力来躲避审查、提升非法网站的搜索引擎排名。

四、受阻：被401和403拦在门外

为了进一步分析攻击者是如何控制这个跳板服务器的，我尝试用 dirsearch 对 malicious.example 进行目录扫描。

结果几乎全是 401 Unauthorized 和 403 Forbidden。

扫描器完全“吃瘪”。这说明 malicious.example 部署了非常严格的访问控制，包括 Cloudflare WAF 和 HTTP 基础认证，是一个高度专业化的跳板服务器。

从扫描结果中，我也提取到了一些有价值的指纹信息：

  • 大量 /WEB-INF/ 路径被拦截，说明服务器上部署了 Java Web 应用；
  • 对 wp-config.php 等文件的探测返回 403，说明可能存在 WordPress 站点；
  • 对 /var/lib/cloud/instance/ 的请求返回 401，说明服务器运行在云平台上。

这些信息虽然不能直接帮我“提权”，但足以证明这台服务器的专业性和攻击者的组织化程度。

五、处置：双线合规上报

确认了完整的攻击链后，我做了两件事：

第一，向某视频平台SRC提交漏洞报告。

我整理了漏洞原理、复现步骤和攻击链分析，按照平台SRC的格式要求提交了报告。虽然最终审核结果是“内部已知”，没有奖励，但这是我第一次完整走通SRC提交流程。

第二，向CNCERT提交政府网站被黑报告。

由于政府网站没有公开的SRC平台，我按照《网络安全事件报告管理办法》的要求，向国家互联网应急中心提交了网络安全事件报告。

报告内容包括：

  • 事发单位：某地政府机关；
  • 初判事件类型：网络攻击事件；
  • 事件经过：从平台漏洞到跳板域名再到政府网站被篡改的完整链路；
  • 已采取的措施：向某视频平台SRC提交漏洞报告；
  • 证据材料：URL解码过程、跳转抓包记录、页面截图。

报告提交后，我获得了一个受理编号（编号已隐去）。

后来我再次访问那个政府网站页面时，发现它已经返回 504 Gateway Timeout，说明页面已经被下线处置了。

六、收获与反思

这次挖洞虽然没有拿到奖金，但收获是巨大的：

1. 建立了攻击链思维

以前我挖洞是“看到一个点就挖一个点”，这次我学会了顺着一条线索一直追下去，把分散的漏洞点连成一条完整的攻击链。

2. 学会了合规处置流程

从平台SRC到CNCERT，我走通了商业平台和公益平台两条上报路径，理解了不同渠道的定位和规则。

3. 体会了白帽的法律边界

在对政府网站进行分析时，我始终坚持“只被动观察、不主动扫描”的原则。政府网站不是SRC目标，未经授权对其进行漏洞扫描是违法的。合规上报才是正确的处理方式。

4. 接受了“没有奖励”的常态

平台SRC判定“内部已知”，政府网站没有奖金。这在漏洞挖掘中是常态——不是每次努力都有物质回报。但能力提升和经验积累，是比奖金更重要的收获。

七、给新手的建议

如果你也是刚入门的安全研究者，我有几点建议：

  1. 保持好奇心：一个奇怪的链接、一个异常的跳转，都可能是漏洞的入口。
  2. 学会解码和分析：遇到编码过的参数，先解码看看它到底想干什么。
  3. 建立攻击链思维：不要满足于发现一个漏洞，试着追踪它最终会通向哪里。
  4. 合规第一：只在授权范围内测试，不碰真实数据，不搞破坏。
  5. 善用工具和AI：遇到卡点不要死磕，及时求助，但求助后要理解原理。
  6. 接受没有奖励的常态：SRC是概率游戏，“内部已知”和“重复”是家常便饭，重要的是持续产出。

八、结语

从视频平台评论区的一条可疑链接，到一条完整的攻击链，再到两份合规报告——这是我第一次SRC挖洞的全部经历。

它没有让我一夜暴富，但让我真正踏进了网络安全的大门。

下一个洞，正在路上。
